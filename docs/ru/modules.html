Модули и импорт

Программа может состоять из нескольких файлов. Один файл подключает другой через import. Здесь описано, что именно подключается, как задаются имена и какие правила проверяет компилятор.

#Простой импорт

Допустим, рядом лежат два файла. Первый — shapes.zk:

shapes.zk
struct Rect { i64 w; i64 h; }

i64 area(Rect r) {
    return r.w * r.h;
}

const auto SIDES = 4;

Второй — главный файл. Импорт пишется в начале:

import "shapes.zk";

void main() {
    const auto r = Rect{ .w = 3, .h = 4 };
    println(area(r), SIDES);
}
Вывод
12 4

Простой import "файл.zk"; кладёт все имена файла (функции, структуры, union, enum, константы, глобальные переменные, псевдонимы типов) в общее пространство имён. Они используются без префикса.

Свойства импорта:

  • Путь — строка, относительно файла, в котором написан import, а не относительно места запуска.
  • Каждый файл загружается один раз, сколько бы раз и откуда его ни импортировали.
  • Импорты можно ставить в любом месте верхнего уровня, но по соглашению их пишут в начале.
  • Подкаталоги допустимы: import "lib/util.zk";.
  • Циклические импорты допустимы: файл загружается один раз, поэтому цикл просто прекращается.

#import ... as имя;

Если имена из файла могут пересечься с вашими, импортируйте с псевдонимом. Тогда все его имена получают префикс имя:::

geometry.zk
struct Point {
    i64 x;
    i64 y;
    i64 sum() { return this->x + this->y; }
}

enum Axis { X, Y }

union Hit { i64 Yes; No; }

const auto ORIGIN_X = 0;

type Coord = i64;

i64 dist2(Point p) {
    return p.x * p.x + p.y * p.y;
}
import "geometry.zk" as geo;

void main() {
    const auto p = geo::Point{ .x = 3, .y = 4 };
    println(geo::dist2(p), p.sum(), geo::ORIGIN_X);
    const geo::Axis a = .Y;
    const auto b = geo::Axis.X;
    println(a, b);
    const geo::Hit h = .Yes(5);
    println(h);
    const geo::Coord c = 7;
    println(c);
}
Вывод
25 7 0
.Y .X
geo.Hit.Yes(5)
7

Псевдоним ставится перед любым членом файла: функцией, типом, константой, глобальной переменной. Формат печати типов тоже показывает префикс (geo::Point{ ... } в сообщении ошибки или при печати структуры).

Внутри самого файла его имена работают без префикса: переименование видят только те, кто импортирует.

Методы и литералы вариантов (.Y, .Yes(5)) не требуют префикса: они выводятся из типа.

#Один файл — несколько имён

Файл загружается один раз, сколько бы раз и под какими бы именами его ни импортировали. Оба имени одного файла работают:

util.zk
i64 tool() { return 1; }
import "util.zk" as a;
import "util.zk" as b;

void main() { println(a::tool() + b::tool()); }
Вывод
2

Поэтому библиотека может импортировать std/thread как thread, а ваша программа — как t. Остаются два правила: имя принадлежит одному файлу, и файл, импортированный где-то с именем, нельзя импортировать ещё и простым импортом (без as).

#Простой импорт «протекает»

Если файл util.zk сам делает простой import "base.zk", то имена из base.zk оказываются в общем пространстве имён и становятся видны везде, в том числе в главном файле:

lib/base.zk
i64 base_val() { return 41; }
lib/util.zk
import "base.zk";

i64 helper() { return base_val() + 1; }
import "lib/util.zk" as u;

void main() {
    println(u::helper());
    println(base_val());
}
Вывод
42
41

Имена из util.zk получили префикс u::, а base_val из вложенного простого импорта — нет. Если хотите изолированный модуль, импортируйте всё через as, и тогда префикс везде будет явным.

#Пути

Путь в import читается от каталога текущего файла. Поэтому lib/util.zk, подключая "base.zk", ищет его рядом с собой, в lib/, а не рядом с главным файлом.

Отсутствующий файл — ошибка при компиляции:

import "missing.zk" as m;

void main() {}
Вывод компилятора
error: cannot read './missing.zk': error.FileNotFound

#extern и export в модуле

extern, объявленный в модуле, подключённом as name, получает префикс, как и всё остальное (name::puts), а символ C, с которым он связывается, остаётся прежним. Поэтому модуль может объявить extern i32 close(i32 fd);, а в вашей программе всё равно может быть своя функция close. export вызывается из C по точному имени, поэтому остаётся глобальным. Подробнее — на странице взаимодействие с C.

#Конфликты имён

Если два простых импорта определяют одно имя, компилятор останавливается с сообщением о дубликате:

one.zk
i64 helper() { return 1; }
two.zk
i64 helper() { return 2; }
import "one.zk";
import "two.zk";

void main() {
    println(helper());
}
Вывод компилятора
two.zk:1: error: duplicate function 'helper'
    1 | i64 helper() { return 2; }

Решение: импортируйте оба с as или переименуйте функции.

Ваши собственные имена и имена стандартной библиотеки тоже не должны совпадать: заводить свою max или sort нельзя (см. справочник).

#Как устроено разбиение на файлы

Нет «пакетов» и файла манифеста. Модуль — это просто файл. Для небольшой программы хватает такой схемы:

project/
├── main.zk        главный файл, содержит main()
├── model.zk       структуры и их методы
├── parse.zk       разбор входных данных
└── util.zk        мелкие помощники

Главный файл подключает остальные:

import "model.zk" as model
import "parse.zk" as parse
import "util.zk"

Запуск: zark run main.zk. Остальные файлы подтягиваются сами.

#Только достижимое компилируется

Компилятор берёт из импортированных файлов только те функции, до которых можно добраться из main. Лишний импорт не раздувает бинарник, а неиспользуемая функция не проверяется на типы (если это не дженерик, ошибки в нём проявятся при первом использовании).

maybe.zk
i64 used() { return 1; }

i64 never_called() {
    return "это не число";
}
import "maybe.zk";

void main() {
    println(used());
}
Вывод
1

Примечание. Ошибка в never_called не обнаружена, пока функцию не вызовут. Если хотите проверку всего кода, вызывайте функции из тестов (см. тестирование).
