Отладка и чтение ошибок

Большая часть времени с новым языком уходит на чтение того, что он говорит. Эта страница учит этому: как устроено сообщение, какие сообщения встречаются чаще всего и как их исправить, и что делать, когда программа компилируется, но всё равно делает не то.

#Как устроено сообщение об ошибке

void main() {
    const auto total = 10;
    println(totl);
}
Вывод компилятора
main.zk:3: error: unknown identifier 'totl' (did you mean 'total'?)
    3 |     println(totl);
      |             ^
  1. Где: файл и строка, затем важность.
  2. Что: одно предложение. Имена в одинарных кавычках — имена из вашего кода.
  3. Сама строка, а под ней каретка ^ у выражения, о котором сообщение.
  4. Подсказка, когда компилятор может догадаться («did you mean ...»).

Читайте первое сообщение первым. Компилятор останавливает функцию на первой проблеме, поэтому последующие сообщения часто исчезают после исправления первого.

#Частые ошибки компиляции и их исправление

Тип не подходит. Компилятор сам не сужает и не меняет знак:

void main() {
    const i64 big = 1000;
    const i32 small = big;
    println(small);
}
Вывод компилятора
main.zk:3: error: type mismatch: expected 'i32', got 'i64'
    3 |     const i32 small = big;
      |     ^

Исправление: напишите big as i32, если потеря битов допустима, или возьмите более широкий тип.

Функция возвращает не на каждом пути:

i64 sign(i64 x) {
    if (x < 0) { return -1; }
    if (x > 0) { return 1; }
}

void main() { println(sign(5)); }
Вывод компилятора
main.zk:1: error: function 'sign' does not return a value on every path; add a 'return' at the end
    1 | i64 sign(i64 x) {

Исправление: добавьте return 0; для оставшегося случая.

Забытая ошибка:

!i64 parse(str s) { return parse_int(s); }

void main() {
    parse("12");
}
Вывод компилятора
main.zk:4: error: error union is ignored; handle it with '?' or 'catch'
    4 |     parse("12");
      |     ^

Исправление: parse("12")? в функции, возвращающей !T, catch со значением по умолчанию или _ = parse("12") catch 0;, если вы правда хотите её проигнорировать.

match, в котором не хватает варианта:

enum Dir { North, South, East, West }

str name(Dir d) {
    return match d {
        .North => "n",
        .South => "s",
        .East => "e",
    }
}

void main() { println(name(.West)); }
Вывод компилятора
main.zk:4: error: match is not exhaustive: missing '.West' (add the arm or a '_' arm)
    4 |     return match d {
      |            ^

Исправление: добавьте .West (именно эта проверка делает добавление варианта безопасным).

Структура, не удовлетворяющая интерфейсу:

interface Shape { f64 area(); f64 perimeter(); }

struct Square {
    f64 side;
    f64 area() { return this->side * this->side; }
}

void main() {
    auto s = Square{ .side = 2.0 };
    Shape sh = &s;
    println(sh.area());
}
Вывод компилятора
main.zk:10: error: 'Square' does not implement 'Shape': missing method 'perimeter'
   10 |     Shape sh = &s;
      |     ^

Исправление: реализуйте недостающий метод.

Строка с фигурными скобками:

void main() {
    println("{"a": 1, "b": 2}");
}
Вывод компилятора
main.zk:2: error: bad format ' 1, "b": 2' after ':': a format is [flags][width][.precision][letter], like {x:08X} or {pi:.3}; to print a literal brace write {{ or }}
    2 |     println("{"a": 1, "b": 2}");
      |            ^

Исправление: литеральная скобка пишется дважды, "{{\"a\": 1, \"b\": 2}}". Интерполяция — это {выражение} или {выражение:формат}.

#Сообщения о владении

Они приходят от проверок, описанных в разделе модель безопасности. В них всегда названы две строки: где что-то перестало быть действительным и где вы это использовали.

void main() {
    const auto a = c_allocator();
    auto buf = a.alloc<u8>(16) catch return;
    a.free(buf);
    buf[0] = 1;
}
Вывод компилятора
main.zk:5: error: 'buf' is used after 'free' consumed it on line 4; assign it a new value first
    5 |     buf[0] = 1;
      |     ^

'buf' is used after 'free' consumed it: строка выше — это free. Либо уберите последующее использование, либо перенесите free после последнего использования, либо сначала присвойте переменной новое значение.

void main() {
    auto l = List<i64>::init(c_allocator());
    defer l.deinit();
    l.push(1) catch return;
    const auto view = l.slice();
    l.push(2) catch return;
    println(view.len);
}
Вывод компилятора
main.zk:7: error: 'view' points into 'l', and 'push' on line 6 may have moved or freed that memory; take the pointer again after it
    7 |     println(view.len);
      |                 ^

'view' points into 'l', and 'push' ... may have moved or freed that memory: возьмите view заново после push.

i64* make() {
    i64 local = 5;
    return &local;
}

void main() { println(*make()); }
Вывод компилятора
main.zk:3: error: returning something that points into local 'local' (a pointer, a slice, or a closure that captured it), which dies when the function returns; allocate it with an Allocator or take a pointer from the caller
    3 |     return &local;
      |     ^

returning something that points into local: локальная переменная умирает при возврате из функции. Верните значение, пусть вызывающий передаст место или выделите память аллокатором.

#Что говорит паника

Паника — это баг в программе. В сообщении есть причина и место:

Сообщение Значение Что искать
index 3 out of bounds (len 3) индекс за концом ошибка на единицу, цикл до len вместо len - 1
slice [2..9] out of bounds (len 5) диапазон среза не помещается арифметику диапазона
division by zero нулевой делитель пропущенную проверку перед / или %
integer overflow результат не помещается в тип слишком маленький тип или имелось в виду +%
assertion failed ложный assert условие и данные, которые до него дошли

Запустите упавший случай ещё раз под -g и gdb, чтобы увидеть переменные.

$ zark build -g crash.zk -o crash
$ gdb ./crash
(gdb) break crash.zk:12
(gdb) run
(gdb) print total
(gdb) bt

-g добавляет в отладочную информацию номера строк, локальные переменные, структуры и массивы. Точки останова по файл:строка работают.

#Программа неправильная, но ничего не падает

  1. Напечатайте данные. println печатает структуру с именами полей и срез с его элементами. Печатайте до и после шага, который подозреваете.
  2. Напишите падающий тест. Положите наименьший вход, показывающий проблему, в блок test, запустите zark test file.zk и правьте, пока не позеленеет. Тест остаётся как защита.
  3. Сократите вход. Убирайте код и данные, пока проблема не останется одна. Причина обычно видна в этот момент.
  4. Спросите другой бэкенд. zark run file.zk, затем zark run file.zk --llvm и -O. В безопасном режиме все они должны печатать одно и то же. Если нет, вы нашли баг компилятора; сохраните файл.

#Проблемы с памятью

Если программа падает с segmentation fault или результат меняется от запуска к запуску, подозревайте память в первую очередь.

  1. Запустите с обработчиком падений (он включён по умолчанию). Строка с причиной скажет null pointer, stack overflow или use after free.
  2. Замените аллокатор на проблемном пути на DebugAllocator (DebugAllocator::init() и dbg.allocator()). Использование после освобождения, даже через копию, останавливается на самом обращении и называет блок. dbg.deinit()? сообщает о блоках, которые так и не освободили.
  3. Если назван номер блока, поставьте dbg.trap_id равным ему и запустите под gdb: программа остановится там, где блок был выделен.

#Когда медленно

$ zark run app.zk --time
time: frontend 12.0 ms, native backend 4.1 ms, link 18.3 ms

Это время самого компилятора. Для времени программы соберите с -O (оптимизировано и по-прежнему безопасно). Если всё ещё медленно и протестировано, --release убирает проверки. Измеряйте до и после: не гадайте.

#Заглянуть внутрь компилятора

Команда Показывает
zark tokens file.zk токены после лексера
zark ir file.zk LLVM IR, который генерирует компилятор
zark fmt file.zk ничего: перезаписывает файл стандартным форматированием (--check только проверяет)

Когда сообщаете о баге компилятора, приложите наименьший файл, который его показывает, команду и вывод.
