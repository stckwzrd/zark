Все инструменты — это подкоманды одного исполняемого файла `zark`. Отдельно ничего ставить не нужно.

## Диагностика компилятора

Любая ошибка печатается в формате `файл:строка: error: сообщение`, под ним показана строка исходника и указатель `^` на место ошибки:

```zark error
void main() {
    const auto count = 1;
    println("{cuont}");
}
```

Когда в программе есть похожее имя, компилятор подсказывает его (для имён короче трёх символов подсказки не показываются, они были бы случайными):

- неизвестная переменная или функция;
- поле структуры, вариант enum или union, имя в списке захвата замыкания;
- имя ограничения дженерика (`T: Orb` → `Ord`).

Типичные сообщения и их причины разобраны на странице [ловушки и FAQ](gotchas.md).

> **Примечание:** компилятор останавливается на **первой** ошибке парсера. Ошибки типов он тоже сообщает по одной за запуск, но [языковой сервер](#языковой-сервер-и-редактор) проверяет каждую функцию отдельно и показывает по одной ошибке на функцию.

## zark fmt

`zark fmt файл.zk ...` переписывает файлы на месте. Форматтер работает по токенам: он правит пробелы, отступы и пустые строки, **никогда не переносит и не склеивает строки** и не трогает комментарии.

```sh
$ cat ugly.zk
//   header comment


import "x.zk";   // trailing


struct P{i64 x;i64 y;}
i64   add( i64 a ,i64 b )  {
return a+b;   // sum
}
void main()  {
auto   p=P{.x=1,.y=2};
	if (p.x==1&&p.y>0){
println("ok {p.x}");
 }else{
    println("no");
}
for (auto i : 0..10){total+=i*2-1;}
match total {
1,2=>println("a"),
_ => { println( "b" ); }
}
const auto r=-q+ (add(q,1)*2);
i64* z=&p;
}

$ zark fmt ugly.zk
formatted ugly.zk
$ cat ugly.zk
//   header comment

import "x.zk";   // trailing

struct P { i64 x; i64 y; }
i64 add(i64 a, i64 b) {
    return a + b;   // sum
}
void main() {
    auto p = P{ .x = 1, .y = 2 };
    if (p.x == 1 && p.y > 0) {
        println("ok {p.x}");
    } else {
        println("no");
    }
    for (auto i : 0..10) { total += i*2 - 1; }
    match total {
        1, 2 => println("a"),
        _ => { println("b"); }
    }
    const auto r = -q + (add(q, 1)*2);
    i64* z = &p;
}
```

Что именно делает форматтер:

- отступы — 4 пробела на уровень вложенности скобок; продолжение выражения на следующей строке получает ещё один уровень;
- пробелы вокруг бинарных операторов, после запятых и двоеточий, внутри `{ }` на одной строке; нет пробелов внутри `()` и `[]`; угловые скобки дженериков (`List<i64>`) остаются как написаны;
- серии пустых строк сворачиваются в одну, пустые строки сразу после `{` и перед `}` убираются;
- пробелы в конце строк удаляются, файл заканчивается ровно одним переводом строки;
- расстояние между кодом и комментарием в конце строки сохраняется как есть.

Чего форматтер **не** делает: не ломает длинные строки, не выравнивает комментарии по колонке, не меняет порядок объявлений, не переименовывает ничего. Пробелы вокруг `*` и `&`, когда по соседним токенам не понять, умножение это или указатель (`i*2` в примере выше), он оставляет такими, какими они были.

`--check` ничего не меняет, а печатает `would reformat файл` для каждого файла, который был бы изменён, и завершается с кодом 1 — удобно для CI:

```sh
$ zark fmt --check ugly.zk
would reformat ugly.zk
$ echo $?
1
```

Форматтер идемпотентен: повторный запуск на уже отформатированном файле ничего не меняет. Он гарантированно сохраняет поток токенов: смысл программы измениться не может.

> **Примечание:** файлы с переводами строк `\r\n` форматтер превращает в `\n`.

## Режимы компиляции

У Zark два бэкенда:

- **собственный x86-64 бэкенд** (по умолчанию). Компилятор сам превращает промежуточное представление в машинный код и пишет ELF-объект. Сборка очень быстрая; код заметно быстрее «наивного», потому что есть распределение регистров, но медленнее оптимизированного LLVM;
- **LLVM** (`--llvm`, `-O`, `--release`): компилятор печатает LLVM IR, а `clang` его оптимизирует и компилирует.

| Команда | Бэкенд | Оптимизация | Проверки границ |
|---|---|---|---|
| `zark run x.zk` | свой | нет | да |
| `zark run x.zk --llvm` | LLVM | `-O0` | да |
| `zark run x.zk -O` | LLVM | `-O2` | да |
| `zark run x.zk --release` | LLVM | `-O2` | **нет** |
| `zark run x.zk --no-safety` | свой | нет | **нет** |

Проверка границ — это то, что превращает выход за массив в понятную панику. Без неё это **неопределённое поведение**: пример ниже падает с `panic` при обычной сборке и молча читает мусор при `--release`:

```sh
$ zark run oob.zk
panic: index 5 out of bounds (len 3) at oob.zk:4
$ zark run oob.zk --release
140735146892504
```

(`oob.zk` читает `a[5]` у массива из трёх элементов.) Отладочные сборки держите с проверками, `--release` включайте для готовых программ, когда уверены в корректности индексов.

Для разработки используйте режим по умолчанию: он собирает сам компилятор (около 25 тысяч строк Zark) примерно за треть секунды, не считая линковки.

## Промежуточные представления

`zark ir file.zk` печатает LLVM IR, который сгенерировал фронтенд. Это тот же текст, который читает собственный бэкенд. Для функции

```zark
i64 fib(i64 n) {
    if (n < 2) { return n; }
    return fib(n - 1) + fib(n - 2);
}
```

получается (локальные переменные лежат в `alloca`, имена `%tN` — временные значения):

```text
define internal i64 @vb.fib(i64 %a.0) {
entry:
  %v.n.1 = alloca i64
  store i64 %a.0, ptr %v.n.1
  %t2 = load i64, ptr %v.n.1
  %t3 = icmp slt i64 %t2, 2
  br i1 %t3, label %then1, label %endif3
then1:
  %t4 = load i64, ptr %v.n.1
  ret i64 %t4
endif3:
  %t5 = load i64, ptr %v.n.1
  %t6 = sub i64 %t5, 1
  %t7 = call i64 @vb.fib(i64 %t6)
  %t8 = load i64, ptr %v.n.1
  %t9 = sub i64 %t8, 2
  %t10 = call i64 @vb.fib(i64 %t9)
  %t11 = add i64 %t7, %t10
  ret i64 %t11
}
```

`zark tokens file.zk` печатает токены: номер строки, вид токена и текст. Полезно, когда непонятно, как лексер разобрал строку (особенно с кавычками и фигурными скобками):

```text
1 .kw_fn fn
1 .ident fib
1 .lparen (
1 .ident n
1 .colon :
1 .ident i64
```

Как устроено всё остальное — на странице [как устроен компилятор](how-it-works.md).

## Языковой сервер и редактор

`zark lsp` — языковой сервер по протоколу LSP на стандартных вводе/выводе. Он построен на том же парсере и генераторе, что и компилятор, поэтому сообщения те же, что при `zark build`, и они относятся и к несохранённым изменениям. Возможности:

| Возможность | Что умеет |
|---|---|
| Диагностика | ошибки с точным диапазоном по ходу набора, подсказки «did you mean», быстрые исправления |
| Подсказка при наведении | сигнатура символа и комментарии `///` над объявлением |
| Автодополнение | члены структур и методы (по выведенному типу) после `.`, `->` и `::`, имена модулей после `alias::`, варианты enum после `.`, поля литерала после `.` внутри `Имя{ ... }`, локальные переменные, глобальные имена, ключевые слова |
| Подсказка по параметрам | при вводе `(` и `,`: сигнатура вызываемой функции или метода |
| Переход к определению | в том числе в импортированные файлы и по пути внутри `import "..."` |
| Ссылки и переименование | по всему рабочему каталогу, включая файлы, которые импортируют ваш файл |
| Структура файла | дерево структур, перечислений, функций, методов и тестов |
| Поиск символов | `Ctrl+T` по всем `.zk`-файлам рабочего каталога |
| Подсветка вхождений | все использования символа под курсором |
| Форматирование | то же, что `zark fmt` |

> **Примечание:** диагностика работает так: сервер запускает фронтенд компилятора по каждой функции файла (кроме обобщённых, они проверяются только когда вызываются) и собирает по одной ошибке на функцию. Парсер останавливается на первой синтаксической ошибке в файле.

Что сервер **не** делает: не показывает типы выражений, не умеет рефакторинг, кроме переименования, и не выводит типы в сложных дженерик-выражениях (там подсказок просто не будет).

### VS Code и code-oss

В репозитории лежит расширение `editors/vscode`. Оно запускает `zark lsp` и добавляет подсветку синтаксиса, сниппеты, кнопки запуска и тестов, команду «Zark: Restart Language Server».

```sh
cd editors/vscode
npm install
python3 pack.py zark-lang.vsix
code-oss --install-extension zark-lang.vsix      # или: code --install-extension zark-lang.vsix
```

После установки перезагрузите окно (`Ctrl+Shift+P` → «Developer: Reload Window») и откройте любой `.zk`-файл. Настройки:

| Настройка | Значение |
|---|---|
| `zark.path` | путь к `zark`; по умолчанию ищется в `PATH`, затем в `~/.local/bin` |
| `zark.trace.server` | `off`, `messages` или `verbose`: журнал обмена с сервером на вкладке вывода |

Горячие клавиши: `Ctrl+Alt+R` — запустить файл, `Ctrl+Alt+T` — запустить тесты. Над `main` и над каждым `test` появляются ссылки «Run». Форматирование при сохранении включено для `.zk` по умолчанию.

### Другие редакторы

Любой клиент LSP подойдёт: команда запуска `zark lsp`, транспорт stdio, расширение файлов `.zk`. Ниже типичные настройки; я не проверял их в каждом редакторе, поэтому считайте их отправной точкой.

```text
-- Neovim (0.11+)
vim.filetype.add({ extension = { zark = "zark" } })
vim.lsp.config("zark", { cmd = { "zark", "lsp" }, filetypes = { "zark" }, root_markers = { ".git" } })
vim.lsp.enable("zark")
```

```text
# Helix: languages.toml
[language-server.zk]
command = "zark"
args = ["lsp"]

[[language]]
name = "zark"
scope = "source.zk"
file-types = ["zark"]
language-servers = ["zark"]
comment-token = "//"
indent = { tab-width = 4, unit = "    " }
```

```text
;; Emacs (eglot)
(add-to-list 'auto-mode-alist '("\\.zk\\'" . prog-mode))
(add-to-list 'eglot-server-programs '(prog-mode . ("zark" "lsp")))
```

Подсветка для Zed, Sublime и других редакторов может использовать грамматику TextMate из `editors/vscode/syntaxes/zark.tmLanguage.json`.

## Отладка

- **`println`** — основной инструмент. Вывод идёт сразу, `eprintln` пишет в stderr.
- **`panic("сообщение {x}")`** печатает сообщение с файлом и строкой и завершает программу с кодом 1.
- **`assert(условие)`** паникует с файлом и строкой, если условие ложно.
- **`zark ir`** позволяет увидеть, как компилятор понял программу, и найти, например, лишние копии агрегатов.
- **gdb**: собственный бэкенд кладёт в файл таблицу строк DWARF. Работают `break файл.zk:12`, `next`, `step`, `bt` с номерами строк; в трассировке функции выглядят как `vb[fib]`, `vb[main]`. Чтобы видеть переменные, добавьте `-g`: `zark build x.zk -g` держит каждую локальную переменную в слоте стека и описывает её, поэтому работают `print x`, `info locals` и `up` (целые, дробные, `bool`, указатели, структуры, массивы и строки; union и интерфейсы пока не описаны). Без `-g` переменные могут жить в регистрах и не описываются. Сборки через `--llvm` и `--release` не содержат ничего, кроме символов функций.
- **`zark tokens`** помогает, когда подозреваете проблему лексера: незакрытая кавычка, фигурная скобка внутри строки и т. п.

## Кэш и временные файлы

Весь мусор сборки лежит в `.zark-cache/` в текущем каталоге: объектные файлы, `.ll` (для LLVM-режима), объекты внешних C/C++ файлов и исполняемый файл `zark run`. Каталог безопасно удалять целиком. Тесты (`zark test`) создают там `имя.test` и `test.out`.

## Переменные окружения и версия

У компилятора нет переменных окружения для настройки. Он вызывает `clang` (и `clang++`, если среди дополнительных файлов есть C++) из `PATH`.
